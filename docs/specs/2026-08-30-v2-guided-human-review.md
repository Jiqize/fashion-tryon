# Fashion Try-on Runner v2 Spec：引导式启动与人工验收

**状态：** 已由用户于 2026-08-30 确认；本文是 v2 阶段的行为事实来源。
**范围：** 在保持本地 CLI + Agent Skill 的前提下，简化启动输入，默认改为人工验收，并让静态报告承担可恢复的返工选择工作。
**基线：** v1 已交付能力继续有效；本文明确变更的行为优先于 v1。

## 背景与目标

v1 已验证“本地素材 → 预检 → 批量换装 → 版本落盘 → HTML 报告”的完整链路，但真人测试暴露出三个问题：

1. 使用者必须在对话里拼出 `scope`、`pairing`、`size`、`maxRetries` 等参数，启动指令过长。
2. 自动质检的尺度难以稳定对应人工审美，可能把整体一致的图片判得过严，也可能漏掉局部问题。
3. 当前报告以大卡片连续展示任务，缺少适合 20–40 个任务的总览、人工判断、选择保存和批量返工闭环。

v2 的目标是：使用者只给一个结构化素材目录，或分别给服装目录和模特目录，即可由 Agent 用一组短问题补齐必要参数；生成后由人快速完成“通过 / 重做”判断，导出可验证的重做清单，再交给 CLI 追加新版本。

## 关键行为

### B1 保持 CLI + Skill 边界

- CLI 仍是唯一业务执行 Interface；Skill 不复制扫描、配对、任务计数、生成、重做或报告逻辑。
- `manifest.json`、`state.json`、`review.json` 与 `events.jsonl` 仍是运行事实。
- `report.html` 仍是可离线打开、可重复生成的派生物，不直接调用 provider，不直接修改运行事实。
- 报告内的人工验收草稿属于浏览器本地工作状态，不得被 CLI 当作运行事实；只有用户显式导出的清单经过 CLI 验证后，才可触发重做。
- 所有输入素材保持只读；人工重做只能向 run 目录追加版本，不能覆盖旧图。

### B2 单目录与双目录启动

- 保留 v1 的单个结构化素材目录输入。
- 新增双目录输入：一个服装素材目录和一个模特素材目录。
- 双目录中的图片按所在输入侧确定角色，不再为角色判断调用视觉模型。
- 两个目录均可递归包含支持的图片；跳过规则、文件上限、稳定排序和输入只读规则与 v1 一致。
- 双目录必须同时存在、可读且各自至少包含一张有效图片，否则 preflight 返回明确问题或错误，不开始生成。
- 单目录和双目录最终都产生同一种任务 manifest；后续 `run`、`resume`、`retry`、`report` 不区分输入来源。
- 现有单目录命令和历史 run 保持可用。

### B3 引导式参数确认

- 当用户只提供路径并调用 Skill 时，Agent 先调用 CLI 的引导式 preflight，不要求用户自己编写完整命令。
- CLI 只返回尚未由用户明确给出的必要选择；Agent 不另造业务问题，也不重复询问已给出的参数。
- 常规路径下最多集中确认以下四项：
  1. 换装范围：`top`、`bottom`、`full`、`full_acc`；推荐 `full`。
  2. 配对方式：`pair`、`fixedModel`、`fixedClothing`；CLI 根据两侧数量给出推荐，但不替用户静默决定。
  3. 输出比例：沿用 v1 支持的比例；推荐 `3:4`。
  4. 质检方式：`manual` 或 `auto`；推荐 `manual`。
- 使用者可以一次回答全部问题，也可以回复“按推荐”。支持结构化提问能力的 Agent 应使用短选项控件；不支持时使用一个简短编号列表。
- 只有选择 `auto` 时，才允许继续确认或覆写自动重出上限；缺省为 `1`。`manual` 模式不询问自动重出次数。
- 素材角色、分组或配对仍存在真实歧义时，CLI 可以追加 v1 已定义的问题；同一时刻可回答的问题应批量展示，不逐个打断。
- 所有问题解决后，Agent 必须展示首轮任务数、当前阶段理论最高生成次数和输出位置，并在得到真实生成授权后才开始付费调用。

### B4 人工质检成为新 run 的默认值

- 新建 run 的默认质检方式为 `manual`；自动质检保留为显式可选能力。
- `manual` 模式中，每个任务首图成功落盘后进入“待人工检查”，不调用自动图片质检，也不自动重出。
- `manual` 模式的首轮理论最高生成次数等于首轮任务数。
- 生成阶段完成可以成功结束，但系统不得把尚未经过人工判断的图片标成“人工通过”。
- 报告中的人工判断与生成状态分开展示：生成成功不等于人工通过，AI 判断也不等于人工决定。
- `auto` 模式继续沿用 v1 的四维质检和有限重出闭环；其结果在新版报告中标为“AI 建议”，不冒充人工验收。
- 历史 v1 run 的自动质检语义保持不变；重新生成新版报告时，只改变呈现，不改写旧账本或旧状态。

### B5 Swiss Research 人工验收报告

- 报告严格遵循 `swiss-research-system/DESIGN.md`，以研究账本而非装饰性卡片墙呈现。
- 视觉系统仅使用白、黑、灰和黄色强调色 `#fde047`；无渐变、无阴影、无衬线标题、无大圆角容器。
- 页面顶部使用黑色基准线、运行编号、标题、说明和关键运行信息。
- 桌面布局包含固定语境侧栏与主任务区；窄屏改为单列，打印时隐藏交互控件和侧栏。
- 所有主要区块使用清楚的 1px 网格边界；统计区使用独立数据卡；任务总览使用有明确表头、行分隔、首列强调和悬停反馈的表格层级。
- 报告必须在 20–40 个任务时仍可快速工作，至少提供：
  - 按任务、款名或素材名搜索。
  - 按“全部、未检查、通过、重做、生成异常”筛选。
  - 总任务数、未检查数、通过数、重做数和生成异常数。
  - 快速跳转到下一条未检查任务。
- 每个任务的总览行至少显示：序号、款/任务标识、scope、生成状态、版本数、AI 建议（如有）和人工决定。
- 展开任务后显示服装参考、当前候选成图、原模特三联对照；图片有 1px 边框、清晰标题和来源说明。
- 历史版本、prompt、AI issues/fix、执行错误和不确定项保留，但作为次级信息收纳，不挤占批量验收主路径。
- 报告不依赖网络、CDN、字体服务或运行中的本地服务器，继续支持直接以 `file://` 打开。
- 所有交互控件有可见键盘焦点、文字标签和可理解的状态，不只依赖颜色表达结果。

### B6 人工决定与本机持久化

- 每个可检查任务有三个互斥的人工状态：`未检查`、`通过`、`重做`。
- 标记“重做”时可填写一条简短原因；原因可为空，且不得被解释为系统命令。
- 人工状态和原因按 run 隔离保存在当前浏览器本地；关闭并重新打开同一报告后必须恢复。
- 不同 run 的选择不能串用；重建同一 run 的 `report.html` 后，只要任务候选版本未改变，已有选择继续恢复。
- 某任务产生了新候选版本后，旧版本上的人工决定视为过期；报告应把该任务恢复为“未检查”并明确提示，而不是把旧决定套到新图上。
- 报告提供显式“清空本次人工记录”动作，并在执行前二次确认；不得自动清空有效选择。
- 搜索、筛选和展开状态无需跨关闭保存；必须保存的是人工决定和原因。

### B7 重做清单导入与导出

- 报告可以导出一个带 schema 版本和 run 身份的 JSON 人工验收清单，默认文件名能识别对应 run。
- 清单包含每个已判断任务的任务 ID、当时检查的版本 ID、人工决定和可选原因；未检查任务不伪装为通过。
- 报告支持重新导入自己导出的兼容清单，以便恢复、转移或核对选择。
- 导入时必须验证 schema、run 身份、任务 ID 和版本 ID；不兼容、跨 run 或过期项不得静默应用，并要显示可理解的错误摘要。
- 导出和导入只操作用户显式选择的 JSON 文件，不修改 `manifest.json`、`state.json`、`review.json` 或 `events.jsonl`。
- 没有标记任何“重做”任务时仍可导出验收记录，但 CLI 不得启动空重做。

### B8 CLI 消费人工重做清单

- `retry` 新增“人工验收清单”选择器，并与现有 `--task`、`--review-failed` 选择器互斥。
- CLI 在任何 provider 调用前验证：schema 受支持、run 身份匹配、任务存在、版本属于对应任务、版本仍是当前候选版本、至少有一个“重做”任务。
- 任一会影响重做对象的验证失败都必须整体拒绝，不进行部分付费重做。
- CLI 只重做清单中标记“重做”的任务；“通过”和“未检查”任务不得生成新版本。
- `manual` 模式下，每个被选任务在一次人工重做中只追加一张新图，不自动质检、不自动继续重出；本轮最高生成次数等于重做任务数。
- 人工原因非空时，作为针对本任务的修复要求加入重做提示；为空时沿用该任务的基础换装要求。
- 旧图、旧 prompt、旧 review 和旧版本索引全部保留；新版本成为新的报告候选图，原人工决定随版本变化而过期。
- Agent 在执行重做前必须报告选中任务数和本轮理论最高生成次数，并再次取得真实生成授权。
- CLI 把已验证的人工重做请求写入运行审计流水，但不把浏览器本地草稿当作账本来源。

### B9 Skill 与使用说明

- Skill 支持以下最短启动表达：一个结构化目录；或“服装目录 + 模特目录”；用户无需记忆完整参数串。
- Skill 优先展示 CLI 返回的短问题和推荐项，接受“按推荐”，再展示任务数与成本上限。
- Skill 在 `manual` 模式完成后返回新版 `report.html`，并用一句话说明“人工标记 → 导出 JSON → 把 JSON 交给 Agent 重做”的流程。
- 用户提供 run 目录与验收清单后，Skill 调用 CLI 的清单重做接口，不手工解析任务并拼接 provider 请求。
- 使用说明的主示例改为路径优先的短表达；完整 CLI 参数下沉为排查参考，不再作为普通用户的首选入口。
- Skill 和文档不得要求用户在对话中粘贴密钥。

## Out of Scope

- 把静态报告改造成 DSH 工作台、常驻服务、MCP server 或远程多用户系统。
- 报告直接调用生图/质检接口，或绕过 CLI 执行重做。
- 报告直接写入或改写 run 的结构化账本。
- 云端同步、跨设备自动同步、账号权限和多人协同审批。
- 在报告中裁图、修图、编辑 mask、拖拽排版或管理素材库。
- 用人工“通过”自动覆盖历史 AI review，或用 AI verdict 自动代替人工决定。
- 为任意未来工作流建立通用表单引擎或万能审核框架。

## 验收标准

1. **短启动：** 只给一个结构化目录并调用 Skill，Agent 一次集中展示必要选项；回复“按推荐”后可完成 preflight，且真实生成前仍显示任务数和调用上限。
2. **双目录：** 分别给服装与模特目录，preflight 不调用视觉角色分类即可形成正确任务；缺失一侧或空目录时不产生付费调用。
3. **人工默认：** 新 run 未指定质检方式时采用 `manual`；含 3 个任务的 fake run 恰好生成 3 张首图，自动质检调用为 0，自动重出为 0，并显示 3 条待人工检查。
4. **自动兼容：** 显式选择 `auto` 时，v1 四维质检与有限重出测试继续通过；历史 v1 run 可生成新版报告且原 JSON 字节不被修改。
5. **批量报告：** 至少 40 个任务的 fixture 在 1440px、1280px 与小于 900px viewport 下无横向溢出；搜索、筛选、统计和下一条未检查均正确，页面无外部网络请求。
6. **设计符合：** 报告具有黑色顶部基准线、固定语境侧栏、1px 网格、数据卡和任务表格层级；只使用规定色板，无渐变、阴影、衬线标题和大圆角卡片。
7. **三联验收：** 任一有成图的任务均可展开查看服装、候选图、原模特以及全部历史版本；图片缺失时显示明确占位，不破坏表格与筛选。
8. **选择恢复：** 在报告中分别标记通过与重做、填写原因并刷新/关闭重开后，状态仍在；其他 run 不出现这些状态；任务候选版本变化后对应旧判断被标为过期并重置。
9. **清单往返：** 导出的 JSON 经重新导入后恢复相同决定与原因；错误 schema、错误 run、未知任务和过期版本均给出错误且不污染已有有效草稿。
10. **选择性重做：** 清单含 3 个通过、2 个重做时，`manual` retry 只为 2 个任务各追加 1 个版本，保留所有旧版本；非空人工原因进入对应重做要求。
11. **付费前拒绝：** 跨 run、空选择或过期清单在 fake provider 调用计数为 0 时失败；Skill 在有效重做前报告 2 个任务、最高 2 次生成并等待授权。
12. **安全与可访问性：** HTML/JSON 不含密钥或绝对私人素材路径；键盘可完成筛选、展开、标记、填写原因、导入和导出，人工状态不只靠颜色表达。
